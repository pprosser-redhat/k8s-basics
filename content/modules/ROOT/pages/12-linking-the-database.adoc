It is generally best practice to separate environment specific configuration from your container image. This helps to ensure that the container image remains portable. In our Parksmap example, the national parks data is held in a MongoDB database and the backend rest application is accessing this data. 

In order to link the database to the back end rest application, you need to tell the back end rest application the name of the host for the database, and what the login credentials are. 

This is a common problem for any application. The need to provide environment specific configuration. In the database example you can be pretty confident that the database host, credentials, and possibly database name will be different between environments. Kubernetes provides a number of ways of passing configuration information to your deployed applications:

* Environment variables (defined in the deployment)
* Configmaps - non confidential data and configuration files. 
* Secrets - sensitive data, e.g passwords, tokens or keys.

When we deployed the MongoDB database, one of the resources that we deployed was a secret which contained connection details for the MongoDB database. Take a look at the secret:

[.console-input]
[source,execute]
----
kubectl get secret mongodb-nationalparks -o yaml
----

In the output you should see the data held in the secret:

[.console-output]
[source]
----
apiVersion: v1
data:
  DB_URI: bW9uZ29kYi1jb21tdW5pdHktc2VydmVy
  database-admin-password: bW9uZ29kYg==
  database-name: bW9uZ29kYg==
  database-password: bW9uZ29kYg==
  database-user: bW9uZ29kYg==
kind: Secret
...
----

Secrets are base64 encoded so we can decode the values to see the raw data. Take one of the base64 encoded strings in your output and decode it as follows:

[.console-output]
[source]
----
echo bW9uZ29kYg== | base64 -d
----

As you can see, if we have access to the secret we can easily find the value. As such, Kubernetes secrets should be protected with additional measures including encyrption at rest and strong RBAC rules to control who can access secrets. External secrets management systems can also be leveraged such as Hashicorp Vault.

Environment variables, Configmaps and secrets can be added to `deployments` so that they are available to applications. Take a look at the backend application to see where the secret is mounted into the containers.

[.console-input]
[source,execute]
----
kubectl get deployment nationalparks-py -o yaml
----

The output will include details of the MongoDB database details being mounted as environment variables from the secret `mongodb-nationalparks`.

[.console-output]
[source]
----
    spec:
      containers:
      - envFrom:
        - secretRef:
            name: mongodb-nationalparks
        image: quay.io/openshiftroadshow/nationalparks-py
----

We learnt how to run commands in pods in the previous lab. Run the following command to list environment variables in the backend application. Scroll through the output and find the environment variables that have been set from the `mongodb-nationalparks` secret:

[.console-input]
[source,execute]
----
kubectl exec deployment/nationalparks-py -- env 
----

[.console-output]
[source]
----
DB_URI=mongodb-community-server
database-admin-password=mongodb
database-name=mongodb
database-password=mongodb
database-user=mongodb
----

Let's break the application by overriding the `DB_URI` variable. To set environment variables, `kubectl` provides the command `kubectl set env`. You are going to update the live configuration change as you'll want to see these commands in action, but keep in mind that best practice would be to modify yaml files to enable the change to easily flow between enironments. Of course, you could add `--dry-run=client` to the command to capture the setting to assist in getting it right.

Change the DB_URI variable to the `wrong-value` as follows:

[.console-input]
[source,execute]
----
kubectl set env deployment/nationalparks-py DB_URI=wrong-value
----

This will result in the backend pod being re-deployed. If you go back to parksmap application in your browser and refresh the screen, you should notice that the application appears to be hanging, similar to the picture below.

image::broken-parksmap.png[Broken Parksmap, 900]

Let's use what we have already learnt to try to debug the issue. Take a look at the logs for the backend application:

[.console-input]
[source,execute]
----
kubectl logs -f deployment/nationalparks-py 
----

It may take a little while, but eventually you should see an error in the logs similar to the following. This shows that we are unable to connect to the MongoDB due to an unknown hostname.

[.console-output]
[source]
----
[Wed Sep 10 10:56:03.919206 2025] [wsgi:error] [pid 24:tid 140452751546112] [remote 10.132.0.155:44792] pymongo.errors.ServerSelectionTimeoutError: wrong-value:27017: [Errno -2] Name or service not known
----

Take another look at the DB_URI environment variable that we changed:

[.console-input]
[source,execute]
----
kubectl exec deployment/nationalparks-py -- printenv DB_URI
----

You should see literally see the wrong-value:

[.console-output]
[source]
----
wrong-value
----

Let's remove the environment variable to fix the application. Adding a hyphen to the end of the environment variable name will remove it:


[.console-input]
[source,execute]
----
kubectl set env deployment/nationalparks-py DB_URI-
----

Wait for the backend deployment to rollout again. Remember, you can check the status:

[.console-input]
[source,execute]
----
kubectl rollout status deployment/nationalparks-py
----

The `DB_URI` variable should now be set from the secret and not overriden. The database and the back end rest application are now linked. Make sure everything is works by looking at Parksmap in the web browser again (you might need to resfresh the page).
